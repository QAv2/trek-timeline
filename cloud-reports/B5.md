## How the project builds

This wasn't fully written down before, so here it is.

- **The site** is static. `docs/` is served as-is by GitHub Pages: `index.html`, ES modules in `docs/app/`, a vendored `d3.min.js` (v7.9.0), self-hosted fonts, `docs/data/archive.json` (the whole archive, about 1.3 MB) and about 4,256 portrait thumbnails in `docs/img/p/`. There is no JS build step and no `package.json`.
- **The data** is rebuilt by Python scripts in `tools/`. They need `requests`, `markdown` and `pillow`, and network access to the Memory Alpha API. `cache/` and `build/` are gitignored scratch space.

```sh
pip install -r requirements.txt
python3 tools/fetch_records.py      # ~981 MA pages -> cache/ma/ (~25 s on first run)
python3 tools/parse_records.py      # -> build/records.raw.json (979 records)
python3 tools/canon_people.py       # optional: refresh data/person_redirects.json
python3 tools/render_briefs.py      # research/<thread>.md -> docs/briefs/
python3 tools/fetch_portraits.py resolve && python3 tools/fetch_portraits.py download
python3 tools/build.py              # -> docs/data/archive.json
python3 tools/smoke_test.py         # new; add --browser for headless Chromium
python3 -m http.server -d docs      # view locally
```

Notes:
- `fetch_portraits.py resolve` reads its people list from the existing `docs/data/archive.json`. New people only get portraits on the second `build.py` run.
- `audit_portraits.py` followed by `fetch_portraits.py pin` is an occasional manual step that swaps portraits shown in the wrong medium (animated vs live action).
- `build.py` drops records that haven't aired as of the day it runs, and stamps that date into `meta.built`.
